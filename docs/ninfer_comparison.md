# NInfer との比較 (フェーズ 9、2026-11-22)

## 計測の条件

- **NInfer**
  - リリース: iamwavecut/ninfer-all 2026-11-22.2 (8f029b0)。Windows x64 CUDA 13.4 版で、チェックサムは一致した。
  - 置き場所: 実行ファイルは `ref/ninfer/bin`、ソース (同じコミット) は `ref/ninfer/src`。ライセンスは Apache-2.0。
  - モデル: WaveCut/Inkling-2-Mini-UD-IQ4_XS-NInfer-v3 (16,494,910,976 バイト、チェックサム一致) を `models/ninfer` に置いた。
- **NInfer の起動設定**
  - コマンド: `ninfer-serve --expert-residency host --host-cache-mib 1024 --spec none`。ポートは 18471。
  - KV は既定の mxfp8。
  - `--host-cache-mib` を付けないと、文脈のホストキャッシュ 8 GiB をピン留めしようとして起動に失敗した (エキスパートの 13.1 GiB と合わせると RAM が足りない)。
- **入力**
  - 自前エンジンと同じトークン列を `/completion` に送り、応答の timings を読んだ。スクリプトは `bench/ninfer_bench.py`、結果は `bench/ninfer_results.csv`。
- **温度 1.0 の条件の違い**
  - 条件は temperature 1.0、top_p 1、min_p 0、seed 1234。
  - NInfer の top_k は 20 が上限なので、語彙全体 (top_k=0) を使う自前エンジンとは候補の数が違う。
- **128K の読み込みの違い**
  - NInfer は 131,072 トークンを毎回最初から読んだ。今回の設定では前の状態を再利用しなかった。
  - 自前エンジンの「後ろの 8K」は、保存した状態を復元してから続きの 8K を読む。

## 移植の候補 (ソースを読んだだけで、実装も計測もしていない。見込みは推定)

1. **ループ状態の生成カーネル**
   - 深さ混合と残差更新を、128 チャネルずつ 1 warp のブロックに分ける。
   - warp ごとの和を、元の 1 ブロック版と同じ順に足すので、結果はビット単位で同じ。
   - 制御器の 9 本の積を 2 回の起動にまとめる。route カーネルの中で、エキスパートごとの並べ替えまで済ませる。
   - NInfer の RTX 3090 (エキスパートは GPU) では、3 つ合わせて生成が 88.9 → 111.4 tok/s。
   - 自前エンジンでは、8K の GPU カーネル時間 9.5 ms/トークンのうち、深さ混合と制御器まわり (mix_conv、ctrl、gemv_rows など) が約 2 ms。
   - 生成 1 トークンではブロックが 1 つしか立たないので、48 SM の大半が空いている。
   - ルーター待ちがそのまま縮むので、見込みは 8K で +5〜10%、128K で +3〜5%。難しさは低〜中。
2. **ホストとの往復をなくす**
   - GPU が振り分けを決め、CPU 用の入力をマップしたホストメモリに書く。GPU 側の待ちカーネルで CPU の和 (固定小数点) を待つ。
   - ただし NInfer 自身も Windows ではこれを切っている。フェーズ 8 の自前の実験 (`INKLING2_CARD_PIPE`) でも Windows では遅くなった。
   - この PC (Windows) での見込みは低い。Linux なら大きい。
3. **ルーティングプロファイル**
   - 形式: JSON `{"version":1,"artifact_id":…,"counts":[[128]×24]}`。
   - 作り方: 生成 (と検証) で通った経路を、層 × エキスパートごとに数える。ループの 3 回分は同じ層に合算する。
   - 使い方: 起動時に回数の多い順にキャッシュを埋める。以後は 4 パスごとに最大 96 個を入れ替える。入れ替えるのは回数が 1.5 以上多いときで、回数は 0.7 倍に減衰させる。
   - 自前エンジンにはすでに `--expert-profile` とオンラインの入れ替えがあるので、得られるのは起動直後の数百トークンの命中率だけ。見込みは定常で ±0%。難しさは低。
4. **CPU と GPU のエキスパートの出力をビット単位で一致させる**
   - 2^-32 の固定小数点で和を取る。int64 の atomicAdd と整数の加算なので、足す順序に依存しない。
   - CPU 側の内積は、GPU のカーネルと同じ丸め順で自前に書き直してある (q8_1 の入力、32 値ごとの整数内積、同じ足し方)。
   - 得られるのは速度ではなく再現性 (振り分けが変わっても出力が同じ)。今のエンジンは greedy でも実行ごとに出力が変わる。
   - 自前エンジンの CPU 側は ggml の内積なので、形式ごとに書き直しが要る。難しさは高。
5. **DSpark の適応ドラフト**
   - 1 回に 3 ドラフト。ドラフターの確率が 0.5 以下になったドラフトまでで切る。
   - 幅は 1〜3 で動かす。基準は「期待される確定トークン数 ÷ 実測の 1 回の時間」で、改善が 1% を超える状態が 4 回続いたら切り替える。
   - NInfer 自身の RTX 5070 (エキスパートはホスト) では 0.98 倍で、逆効果。見込みは ±0〜5%。難しさは低。

## KV q4 の判断材料

- NInfer の Inkling 2 には `rk8v4` と `rk4v4` があり、どちらも回転なし。
  - `rk8v4`: int8 のキー (64 値ごとにスケール) と、パックした int4 の値 (32 値ごと)。1 トークン 12.75 KiB。
  - `rk4v4`: Lloyd-Max 4 ビットのキーと同じ値。1 トークン 8.75 KiB。
  - mxfp8 と int8 は 1 トークン 16.5 KiB、fp16 は 32 KiB。
- 平均 NLL (67,977 トークン、fp16 の 1.784503 に対して): `rk8v4` +0.013%、`rk4v4` +0.062%。どちらも mxfp8 の +0.024% と同じくらいの小ささ。
- NInfer の文書では、Inkling 2 のキーは回転すると悪くなった。
- 自前エンジンの q8_0 から `rk8v4` 相当にすると、128K で KV が約 0.5 GB 減り、エキスパートを約 110 個多く VRAM に置ける。`rk4v4` 相当なら約 1 GB 減り、約 220 個多く置ける。
